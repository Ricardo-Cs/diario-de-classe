ROTEIRO DE ESTUDO DO CÓDIGO — Diário de Aula Virtual
=====================================================

O projeto tem cerca de 22 mil linhas em ~190 arquivos. A ideia é seguir uma
funcionalidade inteira de ponta a ponta (do banco até a tela) e só depois
partir para as mais complexas, que repetem o mesmo padrão.

Caminhos relativos a: app/src/main/java/br/com/ricardo/diariodeclasse/
Tempo total estimado: 20 a 25 horas.


ETAPA 0 — O mapa geral (30 min)
-------------------------------
Objetivo: saber para que serve cada pasta antes de abrir qualquer código.

  data/local/entity  -> tabelas do banco (como @Entity do JPA)
  data/local/dao     -> consultas SQL (como Repository do Spring Data)
  data/repository    -> regras de negócio sobre os DAOs (como @Service)
  di/                -> configuração do Hilt (como @Configuration/@Bean)
  ui/<tela>/         -> *ViewModel (estado) + *Screen (Compose, desenho da tela)
  ui/navigation      -> rotas e barra inferior (como o Router do Angular)
  notificacao/       -> WorkManager e notificações
  data/backup, fotos -> exportação .zip e tratamento de imagens

Para ler: CLAUDE.md, seções 1, 4 e 5.
Você entendeu se: conseguir explicar por que um ViewModel nunca acessa um DAO
diretamente.

[ ] concluída


ETAPA 1 — Como o app liga (1 h)
-------------------------------
- AndroidManifest.xml (em app/src/main/)
- DiarioApplication.kt: o @HiltAndroidApp e a criação dos canais de notificação
- MainActivity.kt
- app/build.gradle.kts e gradle/libs.versions.toml

Conceitos: Application x Activity, ciclo de vida, KSP (gera código em tempo de
compilação, como os annotation processors do Java).
Você entendeu se: souber dizer o que roda primeiro quando ela toca no ícone do app.

[ ] concluída


ETAPA 2 — A camada de dados, só com Turma (2 h)
-----------------------------------------------
Leia nesta ordem:
  1. data/local/entity/EntidadeBase.kt e Turma.kt
  2. data/local/dao/TurmaDao.kt
  3. data/local/AppDatabase.kt e Converters.kt
  4. data/repository/TurmaRepository.kt
  5. di/DatabaseModule.kt e di/RepositoryModule.kt

Conceitos: data class (o copy() substitui o spread do TS), suspend (parecido
com async), Flow (parecido com um Observable que o Room reemite a cada mudança
na tabela), soft delete, UUID, Clock injetado.
Para fixar: abra app/src/test/.../TurmaRepositoryImplTest.kt. Os testes mostram
o comportamento esperado de cada função.

[ ] concluída


ETAPA 3 — A tela, ainda com Turma (2-3 h)
-----------------------------------------
  1. ui/turmas/TurmaViewModel.kt
  2. ui/turmas/TurmaScreen.kt
  3. ui/turmas/FormularioTurmaViewModel.kt e FormularioTurmaScreen.kt
  4. ui/componentes/ (peças reutilizadas em várias telas)

Conceitos:
  - sealed interface UiState (Carregando/Carregado), como uma união
    discriminada do TS;
  - StateFlow + stateIn + combine + flatMapLatest (equivalentes do RxJS:
    BehaviorSubject, combineLatest, switchMap);
  - @Composable e recomposição (lembra o render do React);
  - collectAsStateWithLifecycle, remember;
  - viewModelScope.launch.

Você entendeu se: conseguir descrever o caminho completo de um toque em
"Adicionar aluno" até o nome aparecer na lista. Esta é a etapa mais importante:
daqui em diante todas as funcionalidades repetem o mesmo padrão.
